## 0. 背景、硬底线与验收前提

**背景**：2026-09-22 用户与 codex `gpt-6-astra` 在插件目录内评估了本项目记忆系统，结论是"项目记忆底座不错，差在自动召回、信息更新和记忆维护"。其中第 1 条（预算与可观测性）带有一个可复现实测：**配置 1200 字符的快照预算，实际生成 4731 字符**。本机独立复现确认成立（4672 字符，3.89x）。

**硬底线（一律不改）**：

## 1.（已实施）快照预算：从"分配基准"变成可验证的不变量

### 1.1 问题与复现

```
snapshotCharBudget（配置） = 1200
实际快照长度（字符）       = 4672      ← 3.89x
 1 [1423 字符] ## 长期记忆
 2 [1423 字符] ## 用户档案
 3 [1426 字符] ## 本项目关键记忆
 4 [ 122 字符] ## 记忆与待办 dtodo 工具
 5 [ 270 字符] 收尾两步…
对照：12 条 × 300 字符 → 678 字符（未超预算）
```

### 1.2 根因（三条主路径 + 四类边界）

| # | 根因 | 位置 |
|---|---|---|
| A | auto 的"全量"判定只看**条目数(≤3)与单轨总字符(≤1500)**，与 `snapshotCharBudget`(1200) 量级冲突；单条 1400 字符被判"数据量小"→ 正文全文注入 | `renderTrack` 模式判定 |
| B | 裁剪循环 `kept.length > 1` 保底留一条 → 单条超长永不裁；且"其余 N 条"提示在裁剪**之后**追加，本身不受校验 | `renderTrack` 裁剪循环 |
| C | `snapshotCharBudget` 只用于**分配**三轨配额：固定段先扣不裁、每轨 `max(quota, 150)` 保底 → 合计必然超分 | `renderSnapshot` 配额段 |
| D | core 段的 `identityCharLimit` 判断用 `lines.length > 0` 保护额度，**首条无论如何完整注入**；手写超长 `[summary:…]` 实测把身份段撑到 2063 字符 | `renderSnapshot` 身份段 |
| E | 英文固定段更长（实测 935 字符），英文默认预算下三轨最小形态仍超（1316 > 1200） | 固定段 + 最小轨道形态 |
| F | 各轨 `Math.round` 独立取整、固定块逐个 `+2` 的分隔符近似，使"配额之和 ≤ 可用"本身也不严格 | `allocateTrackQuotas` 调用处 |

**为什么原测试全绿**：`injection-budget.test.js` 的预算是"12 条 × 300 字符"（多条 → 摘要模式 → 裁剪正常工作）；小数据量用例是"2 条 × 20 字符"（远小于任何 softLimit）。**"条目少但每条很长"与"固定段挤占预算"两条路径都没有用例。**

### 1.3 最终实现（`lib/index.js`，五处改动）

1. **降级只作用于 auto**：`if (mode === 'auto' && !summary && render(entries).length > softLimit) summary = true`。
   `mode:'off'` 是显式全量语义——超限时**整条裁掉**，不改变形态（codex 评审发现的首版回归）。
2. **裁剪允许走到 0 条，且取回提示计入长度**：`withHint(list, n)` 在循环内就带上提示行，避免"裁完再追加提示"把软上限顶破。
3. **身份锚点按剩余额度截断**：首条也受限，超出部分用 `expand+id` 取回；`identityLimit` 极小到放不下前缀时不输出该段（零 token）。
4. **配额不再叠加每轨保底**：`softLimit = quotas[track]`（`allocateTrackQuotas` 已保证总和 ≤ available）；删除 `max(quota, floor)`——它正是 700 → 721 超分的来源。
5. **总预算兜底（硬上限的真正来源）**：渲染后按**最终字符串**核对，从配额最小的轨开始**整轨省略**，直到总量落回预算内。
   ```js
   const dropped = new Set()
   const assemble = () => trackInputs.filter((i) => !dropped.has(i.track)).map(renderTrackText).filter(Boolean)
   let trackTexts = assemble()
   const snapshotChars = () => [...parts, ...trackTexts, hintBlock, dutyBlock].filter(Boolean).join('\n\n').length
   for (const input of [...trackInputs].sort((a, b) => quotas[a.track] - quotas[b.track])) {
     if (snapshotChars() <= budget) break
     dropped.add(input.track)
     trackTexts = assemble()
   }
   ```
   省略的是注入而非数据：被省略的轨仍可 `memory action=list/expand` 取回。identity 段已在 `parts` 中、优先级最高，是最后让步的一方。

### 1.4 预算契约（新口径，替换旧的"1200 是硬上限"说法）

- **不变量**：`snapshot.length ≤ max(snapshotCharBudget, 固定段长度)`。
  - 正常配置（zh 固定段 ≈ 450、en ≈ 935，预算 1200）：**上界就是 `snapshotCharBudget`**，与语言无关。
  - 固定段本身超过预算（如 `snapshotCharBudget: 500` + 英文）：快照退化为固定段，这是**物理下限**，属配置错误而非渲染缺陷。
- **core 不是"额外 300 字符预算"**：core 段在 `parts` 里，同样消耗总预算；`identityCharLimit` 只是它**单段行数/长度的上限**。准确说法是"core 优先保留（最后被省略），代价是压缩普通轨配额"。
- **`snapshotCharBudget` 的语义**：常驻注入的**目标且当默认配置下的硬上限**；不包含工具描述、`list/expand` 返回、`buildMemoryContext`（外部执行器）与召回返回——那些是 §4 的"两本账"范畴。

## 2.（规划）接通 DSH 自身会话历史 → 召回链路

### 2.1 现状（实测核对后）

`de_session_search` 是独立子模块（`lib/search/`，`sessionSearchEnabled` 默认 **false**）：

- 数据源只有 **codex**（`lib/search/codex.js`：`~/.codex/sessions`，**archived_sessions 不存在**——codex 已归档路径不存在，本机 44 文件 / 约 109.57MB）；
- **DSH 自身会话完全不支持**（`lib/search/index.js:19-20` 明确记载"zstd 拼接帧暂不支持"）；
- 检索是**字面子串**匹配（无多词/同义），需模型主动调用，无自动召回环节。

**DSH 会话实测口径**（修正首版文档的错误数字）：

| 项 | 实际 |
|---|---|
| `~/.dsh/sessions` | **203 文件 = 151 个 zstd + 52 个 lock**；zstd 中 99 旧格式 + 52 V3 |
| 活跃库体积 | 110,441,591 B ≈ **110.44 MB（压缩后）** |
| `~/.dsh/sessions-archive` | 47 个旧格式，约 33.66 MB；47 个目录 id 均在活跃库出现 → **必须去重** |
| `--home-wenxin-office-dsh--` | 旧 43 / V3 23 / lock 23；9 个会话目录新旧格式并存 |

### 2.2 目标

把"聊天记忆"从"要靠模型想起来调工具"升级为"**先找相关记忆，再组装提示词**"（Mem0 的借鉴点），全程受 §1 同一套预算约束。验收用四道回放题：换一种说法能否找回、旧决定更新后是否还误用、切换项目是否串记忆、隔天续聊是否知道进度。

### 2.3 设计（含关键陷阱）

**A. 源适配层（新增 `lib/search/dsh.js`）**

- **解帧是头号风险（codex 实测）**：DSH 会话是**zstd 拼接帧**，Node 的 `zstdDecompressSync` 与流式 API 都**只解出首帧会话头且不报错**；`zstd -dc` 才能读到全部记录。

  | 样本 | Node 同步 | Node 流式 | `zstd -dc` |
  |---|---:|---:|---:|
  | 旧格式 | 249 B（仅头） | 249 B | 1,289,499 B / 1047 条 |
  | V3 | 272 B（仅头） | 272 B | 1,636,018 B / 349 条 |

  → **"失败才回退 CLI"无效**（不失败）。**P0 直接用 `zstd -dc` 流式读取**，配取消、超时、输出上限、损坏尾帧处理；原生解码要作为优化项，且必须先通过拼接帧完整性测试。
- **schema（实测）**：header 有 `cwd` / `createdAt` / `id` / `agentPreset`；事件用 **`time`**（非 `timestamp`）；用户文本在 `user/message.data.content`；助手文本在 `assistant/message.data.message.content`；usage 在 `assistant/message.data.usage`。
- **归属**：header 的 `cwd` 是权威依据；**目录名只用于候选预筛**（不反解为路径）。`projectHash` 对原始 cwd 字符串求哈希，不自动处理父子目录/软链接/worktree。
- 保留 `source.kind`（插件注入也表现为 `user/message`，不能把所有 user 角色都当作"用户确认"）。

**B. 检索层**

- **源适配表**：`runSessionSearch` 目前硬编码 Codex 的 discovery/parser/rg，需改为"每源自带 prefilter + parser，统一交给 Top-K"。**压缩文件不能交给现有明文 rg 预筛**（要么跳过预筛、要么对解压流做内存匹配）。
- **范围过滤（归 P0）**：`hitForSession` 现在是**大小写不敏感的 cwd 子串匹配**，不是项目隔离——需升级为精确 cwd / 会话 id / 时间窗 / 来源过滤，默认不跨项目。
- **去重**：活跃库与归档的目录 id 重叠（47/47），按会话 id + 时间取新版。
- **返回结构**：加入原始消息 ID 与时间，不只依赖过滤后重编号的 `seq`；现有 4000 字符单消息截断也可能造成漏召回。
- **P1**：用真实语料量化延迟与漏召回；**P2** 才考虑分词/embedding（"向量库应解决已经测出的漏召回问题"）。

**C. 召回层（新增开关，默认关）**

`sessionRecallEnabled`（默认 false）+ `sessionRecallBudget`（建议初始 ≤ 600 字符）；触发时机为会话首轮（续接）与显式"回忆"意图，**不是每轮检索**；输出走同一渲染与预算路径；片段带来源（会话 id + 消息序号 + 时间）作为**证据**，不升级为"当前指令或已确认事实"。

**D. 来源标注**：provenance 先在搜索结果里带上；**持久写回 `source` tag 延后**——新增程序 tag 需要先确认与 `ENTRY_HEAD_RE` / `splitEntryHead` / 替换与合并逻辑兼容（硬底线邻域）。

### 2.4 分期（统一口径）

| 期 | 内容 |
|---|---|
| P0 | `dsh.js` 源适配 + **正确解帧** + 范围过滤 + 去重；仍是手动工具（`de_session_search`） |
| P1 | 真实延迟/漏召回评估（决定是否需要索引、是否上语义检索） |
| P2 | 自动召回（开关 + 预算）+ 来源标注写回 + 工作层联动 |

## 3.（规划）补"工作层"（当前目标 / 已确认决定 / 未解决问题 / 下一步）

### 3.1 为什么

`key` 装长期事实、`project` 日志装"发生了什么"，都答不了"**我们现在做到哪一步**"——新会话只能从 135 条日志里反推进度。gpt-6-astra 把它列为四层结构里"尤其值得补"的一层，同时它是"逐轮写日志"压力的缓解阀。

### 3.2 载体（采纳 codex 的更简方案）

先纠一处事实（首版文档写错）：**未确认的提议不注入，已确认的 `key` 条目是实时注入的**（快照 `lib/index.js:689` 实时读 `KEY.md`；`key add` 才进待确认队列）。当前 key 轨为空，是因为 38 条建议一直没被确认，不是"key 不注入"。

| 方案 | 判断 |
|---|---|
| A 新轨 `working` | 长期可选；但新增配置、同步、冲突与并发覆盖成本，现阶段收益不足以证明 |
| B key 保留区段 | 临时进度会污染长期事实，更新/过期语义也不匹配 |
| C 会话级交接卡 | 可行：缺的是"选哪一份"的机制，不是存储 |

**推荐首版**：在现有 **project 日志**里保存用户确认的"**续接卡**"（沿用现有条目格式，不加轨、不加 tag、不动同步白名单）；新会话**显式选取**并固定一份作为工作视图。若担心日志查询复杂，C 的独立交接卡同样合理。

### 3.3 生命周期（草案）

- 阶段完成只触发**提议**；确认后才替换生效版本，拒绝则保留旧版；
- 按项目 + 任务/分支归属，附来源会话、更新时间、确认状态（避免多会话互相覆盖）；
- **会话首轮加载并固定版本**，显式刷新才更新注入（避免每轮实时渲染导致快照反复变化、破坏前缀缓存）；
- 过期显示**固定**的更新时间和"可能过期"提示，**不要**每次渲染计算变化的"M 天"（那会让快照无意义地变化）；
- 已确认决定若已在 KEY 中，工作视图**引用**即可，不重复写入。

## 4. 横向议题（本轮范围外，但需留口）

1. **预算覆盖所有出口**：本轮只修 `renderSnapshot`。`buildMemoryContext`（`lib/index.js`，外部执行器注入，实测 4325 字符）**完全不复用**这套预算；**且外部 CLI 未必有 `memory expand`**，不能照搬 DSH 的提示文本，需要提供外部可用的全文取回方式，并保留 `[dsh-only]`、分支、tracks 过滤。
2. **可观测性（建议提前）**：先做**字符分项统计**（固定段 / core / 各轨用量 / 裁剪数 / overflow），再做请求级 token 与缓存命中。`usage` 衡量的是整次请求，**不能直接归因"记忆占了多少 token"**。
3. **字符 ≠ token**：`snapshotCharBudget` 是字符预算，中文约 0.6–1 token/字符。
4. **字符 ≠ 上下文成本**：单次快照限长不限制"多次尾部快照累积"；缓存命中也不释放上下文窗口。
5. **事实生命周期**：来源 / 状态 / 有效期 / 替代关系（Graphiti 借鉴）——涉及条目格式扩展，属硬底线邻域，需单独设计。

## 5. 优先级（按 codex 建议调整）
